## 2. Architecture (engine and platform)

### 2.1 Data layers [measured 2026-11-07]

- **Layer 1, catalogue:** 113 ACTIVE products, 84 families, 24 variants; 0 MPN and 0 GTIN on any
  product; `slug`/`display_name` present on all 113 (0 gaps on all three databases).
- **Layer 2, assessments:** 319 `component_assessment` rows over 112 of 113 products, six types.
  Rubric bands contradict on about 27 of 260 rows (R-19).
- **Market data:** `store`, `store_offer`, `price_history`, `ingestion_record`, `product_candidate`,
  `retailer_listing_alias` (0 rows, no reader or writer), `spec_provenance`.
- **Layer 4:** `recommendation_query`, `recommendation_result`, `build_candidate`, `build_component`,
  `build_rejection`, `recommendation_profile`, `recommendation_preset`, `recommendation_swap`.
- **Scoring models:** 7 rows, 6 ACTIVE `launch-v2` versions 1.0.0-2.4.0, `seed-minimal-v1` INACTIVE,
  on all three databases.

### 2.2 Pipeline (`src/recommendation`, in order)

1. **Offer selection:** cheapest eligible offer per product inside a 30-day window (Decision 7),
   `store_offer.id` ASC tie-break; GPU candidates need a non-null `product_variant_id`.
   `SEED_UNVERIFIED` offers are excluded unless `allow_unverified_seed_offers` is on (Decision 35).
2. **Candidate selection**, then **hard filtering** with UNKNOWN semantics; the same rule table is
   registered in `filtering/filter.js` and `assembly/assemble.js`.
3. **Scoring:** weighted quality average minus a penalty per UNKNOWN pair, clamped 0-100. No price.
4. **Retention:** top-K per role inside price bands from `spend_targets` (target ±15 %, ceiling 2x).
   This is where budget currently enters.
5. **Assembly:** deterministic DFS, 25-build cap, per-pair quota.
6. **Ranking:** score DESC, price ASC, signature (code-unit, 2 dp). No randomness, no `localeCompare`.
7. **Archetype selection:** up to 3 pair-distinct builds, `NO_*` codes instead of padding.
8. **Explanation** from one shared `build-facts.js`, then **one write transaction**
   (`orchestrator/commit.js`).

The orchestrator reads inside one `REPEATABLE READ READ ONLY` snapshot with one timestamp as clock.

### 2.3 Invariants worth protecting

- No DB access outside the loaders; no clock, no randomness inside a stage.
- Persistence is append-only where it matters: a swap APPENDS a derived candidate plus a link row.
- Every gate prints PASS, FAIL or INCONCLUSIVE. INCONCLUSIVE is not a pass.
- The API is thin: `apps/api/src/engine.js` is the only module allowed to require the engine.
- The decision log is append-only history (Decisions 1-64); live state belongs in the register.

### 2.4 Ingestion (deliberately network-free)

The seam is a file. `adapters/manual.js` parses an operator CSV or JSON; no code contacts a retailer.
Flow: parse, validate (`listings.js`, `parseMadAmount`), match (`matching.js`), plan (`plan.js`,
dry-run default), apply (`apply.js`), orchestrated by `run.js`.

**Matching tiers:** Tier 0 `CATALOGUE_KEY` (operator gives `product_slug`, plus `variant_sku` when
the product has variants), then SKU exact (CONFIRMED), MPN exact (HIGH), name containment (MEDIUM),
ambiguity to REVIEW. Nothing is ever force-matched.

**Six curated rejection codes, not four** — four live in `resolveCatalogueKey`, two in `buildPlan`:

| Reason | Owner | Meaning |
|---|---|---|
| `UNKNOWN_PRODUCT_SLUG` | `resolveCatalogueKey` | no ACTIVE product carries the slug (typo or inactive) |
| `UNKNOWN_VARIANT_SKU` | `resolveCatalogueKey` | no variant with that sku under that product |
| `VARIANT_SKU_AMBIGUOUS` | `resolveCatalogueKey` | more than one variant matched: a catalogue defect |
| `VARIANT_SKU_REQUIRED` | `resolveCatalogueKey` | the slug's product HAS variants and none was named; a product-keyed GPU offer would never be selectable |
| `VARIANT_SKU_WITHOUT_SLUG` | `buildPlan` | a variant sku means nothing without its product |
| `OFFER_IDENTITY_MISMATCH` | `buildPlan` | the stored offer at `(store, listing_identifier)` names a different product or variant; `apply.js` never rewrites identity, so the row is refused instead |

`retailer_listing_alias` stays 0 rows; a GTIN tier cannot serve GPUs because `product.ean_gtin` is
product-level and `product_variant` has no GTIN column. The provenance gate needs a real
`product_url` whose host belongs to the store's `website_url`.

### 2.5 API

Fastify, contract **v1.10.0**, pinned by an OpenAPI snapshot and a coverage test. **11** routes:
health, meta/options, presets, three catalog routes, docs/json, POST recommendations, GET a pass,
swap-preview, swap commit. No auth, per-IP rate limits, CORS disabled when `ALLOWED_ORIGINS` is
empty, `TRUST_PROXY` empty on Render (Decision 64: one shared bucket). `SCORING_MODEL_PIN`
(Decision 62) selects the served model by `name@version`: malformed throws at boot, unknown answers
503, never a fallback. No response body names the pin; the durable record is
`recommendation_query.scoring_model_id`.

## 6. What needs revision (ranked)

**A1. Offer freshness is a hard dependency with no safety net (HIGH).** Every build needs one fresh
offer per role. **EU's first SEED expiry is 2026-11-17** [measured 2026-11-07], not 2026-12-01 as
earlier drafts inferred; shared expires 2026-12-01, TEST is already expired and assembles zero builds
from seeds. Also unconfirmed: whether the deployed EU service has `allow_unverified_seed_offers` on.
Direction: confirm the date and the flag, then choose between re-dating seeds (labels stay
`SEED_UNVERIFIED`), a wider beta window, or enough real offers.

**A2. Cheapest-first offer selection can hide real data (HIGH).** If a cheaper fresh seed offer
coexists with a dearer real one, the seed wins. Every real price found is higher. Proposed decision
(not yet written): VERIFIED offers outrank SEED_UNVERIFIED regardless of price, cheapest-first within
a class. It touches `offers/select.js`, golden assertions, provenance reporting and the preset shelf.

**A3. Presets are coupled to catalogue and offers (MEDIUM).** A preset is keyed by catalog version
and cannot be copied between databases. Importing real offers or adding products probably changes the
catalog version and stales the shelf. Regenerate presets after any catalogue or offer change. The
stored shelf is 1080p-class because it was generated without a resolution.

**A4. Catalogue growth is bottlenecked by hand-authored assessments (HIGH).** Every new product needs
`component_assessment` rows (~2.8 per product) written by hand against a rubric that contradicts
itself (R-19). Decision to follow local supply makes this the main scaling constraint.

**A5. Identity model limits (MEDIUM).** `ram_spec` has no timing column, so Vengeance RGB RS versus
RGB PRO is indistinguishable. `slug` is nullable but the API drops rows without one. GTIN cannot serve
GPUs. `retailer_listing_alias` should be retired or redesigned. Curated matching trusts the operator:
a wrong-but-valid slug passes, so each curated row needs a second reviewer.

**A6. No path for availability-only updates (MEDIUM).** Out-of-stock listings publish no usable
price, the collector emits no row, and the existing offer ages past the 30-day cliff instead of being
marked unavailable.

**A7. Budget handling lives in the wrong layer (HIGH for product claims, defer).** Budget enters only
through retention bands, so under-spend is a selection symptom. Decision paper recommends a spend band
at the selection layer; decide it now, build it after real prices.

**A8. Low-budget dead zone (MEDIUM).** 6 000 MAD gaming and workstation return zero builds while
`budget_floor.within_budget` is true. Accepted as contract (R-09); real prices will move the band up.

**A9. Provenance and observability gaps (LOW to MEDIUM).** Presets store `engine_version =
generate-presets`, so a stored pass does not name its deploy SHA. `as_of` is not persisted (R-23,
needs a migration). Reason codes are not persisted (R-18). No response names the pinned model.

**A10. Environment and process hygiene (MEDIUM).** TEST is not a mirror. `run-seeds.js` replays
everything and has no routing. The importer has no restore-point flag, so a shared or EU import needs
a manual Neon restore point plus `--confirm-shared`. Several gates are nightly-only. The docs sat
unpushed for a day and `origin/master` briefly contradicted the databases.

**A11. Latency and plan (MEDIUM).** One full POST took 3 209 ms on the 0.1 CPU free instance against
a 3 000 ms target, so there is no valid V1 latency figure. Needs the 0.5c-512mb plan before measuring.

**A12. Sentry off, one global rate-limit bucket, no auth (LOW now, required before public launch).**

## 10. Operational traps

- Seeds: apply only named files, one transaction each, `SET search_path = public`, never split on
  semicolons. Seeds 024 and 025 embed BEGIN and COMMIT, so an outer rollback does not cover them.
  Seed 026 is UPDATE-only, so row counts cannot verify it.
- Never run `run-seeds.js` against a shared database. Replaying the set is how five extra models
  became active on shared.
- EU env: use the preload form `DOTENV_CONFIG_PATH=.env.eu node -r dotenv/config ...`.
- Warm Render services before a role check, or the answer is INCONCLUSIVE.
- `node -e` mangles single quotes in this shell. Use a quoted heredoc or a temp script **inside the
  repo root** (a script in `/tmp` cannot resolve `dotenv`/`pg`).
- CSV: quote any field containing commas. An unquoted `source_note` shifted columns during the
  rehearsal.
- Importer: `store_name` must equal `store.name` exactly; dry-run is the default; each run creates one
  `ingestion_record` even if unchanged; use `--test-db` for TEST.
- Do not re-run `apply-api-role.js` on EU (it refuses an existing role by design). A Neon branch
  restore does not undo a role password change.
- Run `npm ci` before `test:scripts` / `test:api`: without `node_modules` those suites fail on missing
  `dotenv` / `@sinclair/typebox`, which looks like a code failure and is not one.
- Collection etiquette if scraping resumes: obey robots.txt, at least 8 s between requests, stop on
  403 or 429, never bypass a block, honest User-Agent `morocco-pc-price-research/0.1`, skip
  pcstore.ma and iris.ma.
