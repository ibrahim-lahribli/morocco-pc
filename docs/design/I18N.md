# Internationalisation (S5)

**What this file is.** The reference for the bilingual skeleton: how a URL
chooses a language, where copy lives, how a number or a date becomes text, and
what the font strategy costs. The measurement is `apps/web/e2e/i18n.spec.ts`;
the rules that keep it true are two grep gates.

**The contract in one line:** every page is a document with a `lang`, a `dir`
and a URL; every amount and date comes from `Intl` through one helper; and no
client component knows the locale unless the server told it.

## 1. Routing

| URL | Result |
|---|---|
| `/` | 307 → `/fr` |
| `/fr`, `/fr/format` | French, `lang="fr" dir="ltr"` |
| `/ar`, `/ar/format` | Arabic, `lang="ar" dir="rtl"` |
| `/de`, `/ar/kit` | 404 |
| `/fr/kit`, `/fr/tokens` | French-only design proof sheets (`noindex`) |

- **Locale prefix always** (`/fr/...`, `/ar/...`). One URL per language means
  hreflang and canonical tags are exact, a shared link shows the language the
  sender saw, and a URL fully identifies a cacheable document.
- **`proxy.ts`** (Next 16's rename of `middleware.ts`) turns `/` into `/fr` and
  nothing else. Its matcher skips API routes, Next internals and file requests.
- **`i18n/request.ts`** resolves the locale from `next/root-params` (Next 16.3+),
  not from a cookie or `Accept-Language`. That is what keeps `/fr` and `/ar`
  STATICALLY rendered: the build lists both in `generateStaticParams`, and no
  page reads request state. Verified 2026-10-20: 6 prerendered routes (the build
  reports 9 static pages), no dynamic route.
- **An unknown locale is a 404**, raised in the layout and page with
  `hasLocale`. The request config falls back to the default locale instead of
  throwing — a throw there surfaces during export as an opaque digest with no
  message, which cost real debugging time in S5.

## 2. No `NextIntlClientProvider` — and what that costs

next-intl's `Link` is a **client component**: its `BaseLink` calls
`useLocale()` unconditionally (verified in
`node_modules/next-intl/dist/esm/development/navigation/shared/BaseLink.js:46`).
Using it in a server layout therefore requires wrapping the app in
`NextIntlClientProvider`, which ships the message catalogue to the browser so
two links can know the current locale.

This app has no client component that needs translated copy. So instead:

- internal links are `next/link` with `localePath(locale, path)` — one helper,
  one place a `/{locale}` prefix is added;
- the locale switcher receives `active` as a **prop** from the server layout and
  reads only `usePathname()` from `next/navigation`;
- `getTranslations` runs on the server, so the browser receives HTML, not
  messages.

The trade-off is explicit: a language switch is a full document load, not a
client transition. That is correct here (different `lang`/`dir`, different
document), and it means the client bundle carries no i18n runtime at all. S7 can
adopt next-intl's `Link` the moment a client component genuinely needs
translations — the provider then buys something.

`i18n/navigation.ts` was written, then removed in the same sprint: it was a
module whose only consumer would have forced the provider.

## 3. Messages

`messages/fr.json` and `messages/ar.json`, one namespace per surface
(`shell`, `home`, `formats`). Nothing else holds product copy: the test "no
message key leaks into the page" fails if a missing translation renders as
`shell.language` instead of text.

The proof sheets (`/kit`, `/tokens`) are French-only by construction: their
`generateStaticParams` returns `[{locale: "fr"}]` and every other locale 404s.
Rendering French documentation under `lang="ar"` would make a screen reader
pronounce French with Arabic phonetics — an honest 404 is better. S20 translates
product screens; documentation is not a product screen.

## 4. Formatting — one helper, two decisions

`lib/i18n/format.ts` exports `formatNumber`, `formatMoney`, `formatDate`,
`formatPercent`. Nothing else may call `Intl`; `npm run check:i18n` fails on
`new Intl.`, `.toLocaleString()`, a hand-written amount or a literal date
anywhere in `app/`, `components/` or `lib/`.

**Decision 1 — the grouping separator is normalized.** CLDR formats `fr-MA` and
`ar-MA` with a full stop: `7.300`. To a French reader a full stop is a DECIMAL
separator, so `7.300 DH` can be read as seven dirhams and thirty centimes. The
helper rebuilds the string from `formatToParts` and swaps only the group part for
U+202F NARROW NO-BREAK SPACE; digits, sign and the locale's decimal separator
still come from ICU. The design board also writes space-separated groups.

**Decision 2 — the unit is a word, not `Intl` currency style.** `MAD` formats as
`7 300,00 MAD`: cents nobody quotes, and the wrong label for Moroccan copy, which
writes `DH`. The map lives in one place (`CURRENCY_LABEL`) so S20 can switch the
Arabic label to `د.م.` without touching a call site.

Measured output (2026-10-20, Node 24 ICU):

| Input | `fr` | `ar` |
|---|---|---|
| money `7300` | `7 300 DH` | `7 300 DH` |
| date `2026-10-12` | `12 octobre 2026` | `12 أكتوبر 2026` |
| number `1234567` | `1 234 567` | `1 234 567` |
| percent `0.73` | `73 %` | `73 %` (with RTL marks) |

`ar-MA` uses Latin digits — that is CLDR's choice for Morocco, not a fallback
that failed.

## 5. Fonts and CLS

- All three faces are compiled in the one root layout. The **IBM Plex Sans
  Arabic** variable class is on `<html>` for BOTH locales: it is only a CSS
  variable, so nothing downloads unless an element uses the family — and that is
  what makes `font-arabic` resolve on `/fr/tokens`, where the type specimen shows
  the Arabic face. Before the 2026-10-20 review the class was `ar`-only, so
  `font-arabic` was an undefined `var()` on French pages and the specimen silently
  rendered in Inter. The BODY face stays locale-scoped (`html[lang="ar"] body`),
  so a French page paints in Inter.
- **`preload` is per document, not per language, and that costs real bytes.**
  `/fr` carries four IBM Plex `rel="preload"` subset files (~137 KB, measured
  2026-10-20) for a page that renders no Arabic. Turning `preload` off was tried
  and REJECTED: the face then swaps after first layout and the Arabic label in
  the switcher reflows its neighbours by 3 px, which is 0.0007 CLS — the pinned
  scenario is 0. Closing the bytes needs per-locale root layouts or a
  self-hosted face whose URL can be preloaded conditionally; that is S6 budget
  work and is recorded in the layout's header comment.
- `next/font` self-hosts the files, preloads the face, and injects
  metric-adjusted fallback faces (`size-adjust`, ascent/descent overrides) — which
  is what makes the swap shift nothing.
- `html[lang="ar"] body` switches to the Arabic face through the
  `--font-arabic` token; the token still carries its own fallback chain for the
  case where the variable is absent.
- **CLS = 0, measured.** `e2e/i18n.spec.ts` installs a `PerformanceObserver` for
  `layout-shift` BEFORE any app code runs, loads `/ar`, waits for
  `document.fonts.ready`, and asserts both that the cumulative value is 0 and
  that no individual shift was recorded. That is the same signal Lighthouse
  aggregates; Lighthouse itself is S6's CI work, and the local claim is
  deliberately narrower than "Lighthouse CLS = 0".

## 6. What the tests pin

`e2e/i18n.spec.ts`, 13 specs:

- `/ar` has `lang="ar" dir="rtl"` in the server HTML; `/fr` is `fr`/`ltr`;
  `/` redirects; `/de` is 404; no message key leaks;
- the switcher keeps the path (`/fr/format` ↔ `/ar/format`), marks
  `aria-current`, carries `hreflang`, and is a 44 px target;
- money contains a narrow space and `DH` in both locales; dates equal
  `Intl.DateTimeFormat` output computed in the test; numbers and percentages are
  grouped by the helper;
- `/ar` loads IBM Plex Sans Arabic and `/fr` does not apply it;
- CLS is 0 through the font swap.

## 7. Not in S5

- Arabic product copy and the full RTL pass — S20.
- hreflang alternates, canonical tags and sitemap — the SEO surface (S16+).
- A locale cookie or a remembered preference: the URL is the preference.
- Lighthouse budgets and CI wiring — S6.
